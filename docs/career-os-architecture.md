# Career OS architecture (JobAppy / prep.evolw.in)

Written 2026-09-25 after inspecting the repository. This document records what exists, what Phase 1 adds, and how the later phases are meant to build on it without rewrites. Every "existing" claim below was read from the code, not assumed.

## 2. Schema additions (Phase 1, migration `0005_career_os_phase1.sql`)

All ids are text (uuid strings), matching existing tables. Timestamps are `timestamp` columns with defaults, matching `subscriptions` / `curriculum_tracks`.

- `user_roles (userId FK users cascade, role, grantedBy, createdAt; PK(userId, role))`. Roles: `admin`, `content_editor`, `jobs_editor`, `support`.
- `admin_audit_log (id PK, actorId FK set null, action, entityType, entityId, before jsonb, after jsonb, createdAt)`.
- `companies (id PK, name, slug unique, website, careersUrl, logoUrl, headquarters, industry, size, description, status active|hidden, createdAt, updatedAt)`.
- `job_sources (id PK, name, slug unique, type manual|career_page|ats_api|provider|partner, baseUrl, termsUrl, ingestionAllowed bool, notes, status active|paused, createdAt, updatedAt)`.
- `jobs (id PK, companyId FK, sourceId FK set null, title, normalizedTitle, roleCategory, careerPathIds jsonb, trackIds jsonb, description, requirementsSummary, requiredSkills jsonb, preferredSkills jsonb, level, employmentType, workMode, locationCity, locationCountry, region india|international, salaryMin, salaryMax, salaryCurrency, salaryPeriod, applyUrl, sourceUrl, externalId, fingerprint unique, status draft|published|expired|archived, postedAt, expiresAt, lastVerifiedAt, createdBy, createdAt, updatedAt)`. Indexes on `status`, `companyId`, `roleCategory`, `region`, `postedAt`.
- `learner_job_preferences (userId PK FK cascade, roleCategories jsonb, skills jsonb, experienceYears int, locations jsonb, regionPreference any|india|international, workModes jsonb, levels jsonb, employmentTypes jsonb, salaryMin int, salaryCurrency, updatedAt)`.
- `platform_settings (key PK, value jsonb, updatedBy, updatedAt)`. Phase 1 keys: `features` (feature flags) and `entitlements` (tier → feature keys).

Deferred (Phase 2+): `skills` catalogue table, `job_categories` table, `learner_resumes`, `job_matches` cache, `job_ingestion_runs`, `announcements`, `plans` / `plan_features`, `usage_counters`.

## 3. Admin architecture

- Route group `src/app/admin/**` (server components). `layout.tsx` calls `requireAdminPage()`; a signed-out or non-admin visitor gets `notFound()` so the panel's existence is not advertised. The same check guards every `/api/admin/*` route handler with a JSON 403.
- RBAC lives in `src/lib/server/rbac.ts`: `getRoles(userId, email)` reads `user_roles`, then adds bootstrap roles from env (`PLATFORM_ADMINS` → `admin`, `CURRICULUM_ADMINS` → `content_editor`) so the first admin never needs SQL. `requireRole(...)` is the only gate used by routes.
- Every mutation goes through `src/lib/server/audit.ts` (`recordAudit`) inside the same request, storing before/after snapshots. `/admin/audit` lists them.
- Pages are server-rendered lists with search, filters and pagination (URL search params) and client forms (`src/components/admin/*`) that call `/api/admin/*` and then `router.refresh()`. Styling lives in `src/careerOs.css` (imported by the root layout) on top of the existing design tokens.
- Sections implemented in Phase 1: Dashboard, Users & roles, Companies, Job sources, Jobs, Platform settings (feature flags + tier entitlements), Audit log. Later sections (curriculum, interview questions, mock config, plans, announcements, usage limits) attach to the same shell, RBAC and audit helpers.

## 4. Job ingestion architecture (implemented in Phase 2)

Implemented: `src/lib/ingestion/` holds the provider contract (`types.ts`), adapters (`providers/greenhouse.ts`, `lever.ts`, `ashby.ts`, plus a development-only `fixture.ts`), deterministic normalisation (`normalize.ts`) and the engine (`engine.ts`). The engine takes a database handle (node-postgres in the app, PGlite in tests), so idempotency and deduplication are tested on real SQL. Admin surfaces: `/admin/ingestion` (provider health, runs, sweep), `/admin/duplicates`, provider fields on `/admin/sources`; routes under `/api/admin/ingestion/*`. Sources carry `provider`, `config`, `companyId`, `autoPublish`, `lastRunAt/Status/Error`; runs are recorded in `job_ingestion_runs`. Lifecycle: `discovered` (first seen) → `verified` (seen again or admin verify) → `stale` (missing from the source or unseen 7 days) → `expired` (unseen 21 days or past `expiresAt`); learners never see expired jobs and stale ones carry a warning. Remote eligibility is stored separately from work mode (`remoteEligibility`, `eligibleCountries`) and only from what the source states; unknown stays unknown.

Scheduling (Phase 3): `src/lib/ingestion/scheduler.ts` runs every enabled, allowed provider source with a per-source database lock (`lockedAt`/`lockToken`, 15-minute stale timeout), retries transient errors with exponential backoff (configuration errors are not retried), records attempts/duration/trigger per run, keeps `lastSuccessAt`, isolates failures per source and finishes with the lifecycle sweep. Entry points: `POST /api/admin/ingestion/schedule` (admin, audited) and `GET /api/cron/ingestion` (inert until `CRON_SECRET` is set; no cron is configured in the repository).

Original plan (kept for context):

- A `job_sources` row is the provenance record for every job: type (`manual`, `career_page`, `ats_api` such as Greenhouse/Lever/Ashby public JSON feeds, `provider`, `partner`), base URL, terms URL, and an `ingestionAllowed` flag that an admin sets after reviewing the terms. Ingestors refuse sources with `ingestionAllowed = false`.
- Ingestors are pure functions `(source) → NormalizedJobInput[]`, run by an admin-triggered route or a scheduled job (Vercel cron). Each run is recorded (`job_ingestion_runs`, Phase 2) with counts of created / updated / expired jobs.
- Phase 1 has only the `manual` path (admin CRUD), but jobs already carry `sourceId`, `sourceUrl`, `externalId`, `fingerprint`, `lastVerifiedAt` so ingested and manual jobs are indistinguishable to the learner UI.

## 5. Job normalization and deduplication

`src/lib/jobs/normalize.ts` (pure, shared client/server):

- `normalizeTitle`: lower-case, strips punctuation, seniority noise ("(Remote)", "- Bengaluru"), collapses whitespace.
- `jobFingerprint(company slug, normalized title, location, applyUrl host+path)`: deterministic FNV-1a hash stored in `jobs.fingerprint` with a unique index. Admin create rejects duplicates with a clear message; ingestion upserts on it.
- `canonicalApplyUrl`: keeps scheme/host/path, drops tracking query parameters (`utm_*`, `gh_src`, `ref`, `source`).
- Freshness: `jobFreshness(job, now)` returns `fresh` (< 14 days since `postedAt` / `lastVerifiedAt`), `aging` (14–30 days), `stale` (> 30 days) or `expired` (past `expiresAt`). Learner queries exclude `expired` and anything with a past `expiresAt` at query time; a nightly sweep (Phase 2) flips those rows to `expired`.

## 6. Job matching architecture

Implemented in Phase 2: `src/lib/jobs/compatibility.ts` computes a deterministic report (target role 20, required skills 30, preferred skills 10, experience 15, curriculum progress 15, location/work mode 10 = 100). Every component carries its points and a sentence explaining them; the UI shows the table and labels the number "profile / job alignment". The report runs on the client because curriculum progress lives in the learner's Storage document; the server gate `POST /api/jobs/[id]/analysis` enforces the `jobs.matching` feature and the per-day usage limit (`usage_counters`). Gap analysis (`curriculumMap.ts`) labels each relevant track covered / learning / not covered using the skill lexicon's track mapping (`skills.ts`) and career-path tracks, capped at eight; "Add gaps to learning plan" adds only confirmed tracks to the active goal and schedules them with `scheduleTrackIntoRoadmap`.

Original plan (kept for context):

- Phase 1 (`src/lib/jobs/relevance.ts`): a transparent rule-based relevance score from learner preferences only (role category, skills overlap, experience band, region, work mode, level, employment type). Each contribution is returned as a reason string so the UI can show "Why this is shown". It is a ranking aid, never labelled as a hiring probability.
- Phase 2: a full compatibility analysis combining profile + goal + curriculum progress + resume + job description. Deterministic parts (skill overlap, experience fit, curriculum alignment from the registry, location fit) are computed in code; AI is used only to extract structured requirements from the description and to phrase recommendations. Results are cached in `job_matches` keyed by (userId, jobId, inputsHash). Output is always split into "facts" (from the job) and "AI suggestions" (visually distinct).

## 7. Resume analysis architecture (implemented in Phase 3)

- Storage: `resumes` (metadata + file bytes in a `bytea` column, sha256, versions with one `isCurrent`), `resume_profiles` (extracted text + structured profile, extractor version, warnings) and `resume_analyses` (report + suggestion review state, unique per user/resume/job, cascade-deleted with the resume). Every server function in `src/lib/server/resumes.ts` filters by the owner's user id; routes under `/api/resumes/*` return 404 for anything not owned. Files are validated by bytes (`%PDF-` or plain text, ≤ 2 MB), filenames sanitised, download is owner-only with `no-store`; resume content is never logged or sent to an outside provider (extraction is `pdf-parse` in-process, analysis is rule-based).
- Extraction (`src/lib/resume/extract.ts`): deterministic section detection, skill lexicon, dated employment entries, projects, education, certifications, achievements; every entry carries evidence (line numbers + quote); fields that cannot be read are listed in `unknown`.
- Analysis (`src/lib/jobs/resumeAnalysis.ts`): per job skill, `demonstrated` (in an employment bullet or project), `weak` (only listed) or `missing`; strong matches always cite lines; suggestions never propose adding a skill the resume lacks, they point at the curriculum track instead. Suggestions can be saved, dismissed or completed; the uploaded file is never modified.
- Application strategy (`src/lib/jobs/strategy.ts`) assembles job facts, resume evidence, curriculum progress and recommendations with a provenance tag on every line and an explicit "does not guarantee an interview" note. Gates: `jobs.resumeAnalysis` (+ `resumeAnalysesPerDay` usage limit) and `jobs.applicationStrategy`; free accounts keep `resume.profile`.
- Job workspace: `src/JobDetail.tsx` tabs Overview → Match → Curriculum gaps → Resume → Application strategy → Tracker; tracker entries created from a listing carry `jobRef` (job id, company id, resume analysis id) on the existing `JobApplication`.

Original plan (kept for context):

- `learner_resumes` stores the parsed text plus a structured extraction (skills, roles, projects, education) the learner confirms. The analysis compares the confirmed structure with the job's requirements. Prompts forbid inventing experience; the UI only offers rewrites of existing bullets and flags gaps. Uses the existing AI gateway (`/api/ai/chat`, learner or shared keys) and `requireAccess`.

## 7b. Networking, referrals and job preparation (implemented in Phase 4)

- Networking (`src/lib/jobs/networking.ts`): contact *categories* with reasons (never named people), copyable LinkedIn people-search queries (company + role / recruiter / manager + domain / required skill / learner institution or previous employer from the resume), and message drafts (connection, recruiter, referral, hiring-manager, follow-up, thank-you) assembled only from a `DraftGrounding` built from the resume profile and the stored resume analysis; the contact name is always a placeholder and every fact used is listed with its source. Drafts are generated server-side (`POST /api/jobs/[id]/drafts`, usage-limited) so the resume never leaves the server; the learner copies and sends manually. Nothing is scraped or automated.
- Outreach log (`outreach_contacts`, `/api/jobs/[id]/outreach*`, feature `jobs.outreachTracker`): learner-entered name, role, type, profile URL, message type, date, status (nine states), follow-up date, notes and the saved draft, always attached to a job; owner-scoped.
- Preparation (`src/lib/jobs/prepare.ts`): deterministic blueprint (must / revise / strong skills, DSA depth by role and level, framework and language items, CS fundamentals by role family, system-design depth never assumed for entry level, projects only from the resume, behavioural areas grounded in resume bullets) where every curriculum item is a `TopicPointer` to an existing track → topic → first concept resolved through the registry; the interview kit reuses those pointers and labels prompts as curriculum quiz or generated practice. Stored per user/job in `job_preparations` with the chosen duration, plan metadata and manually completed items.
- Plans (`src/lib/jobs/prepPlan.ts`): 7/14/30-day plans call the existing `fillRoadmap` with a temporary topic selection on the learner's active goal, so hours per day, rest days, prerequisites, existing and completed tasks are respected and no curriculum step is duplicated; new tasks carry `prepJobId`. The learner sees a preview and confirms "Add preparation plan"; confirming counts against `preparationPlansPerDay`.
- Readiness (`computeReadiness`): factual counts only (curriculum coverage, required skills demonstrated, preparation areas and tasks completed, resume recommendations done, application status, networking status), phrased as "N of M identified preparation areas completed".
- Job workspace tabs: Overview → Match → Curriculum gaps → Resume → Application strategy → Networking & Referrals → Prepare → Tracker. Free tier keeps `jobs.networkingBasic` (categories, searches, connection/recruiter drafts with a small daily allowance) and `jobs.preparationBasic` (curriculum-only overview); paid adds `jobs.referrals`, `jobs.outreachTracker`, `jobs.preparation`, `jobs.interviewKit`, `jobs.readinessAdvanced`, all admin-configurable with the `messageDraftsPerDay` and `preparationPlansPerDay` limits.

## 7c. Job-specific mock interview intelligence (implemented in Phase 6)

One mock-interview system, two entry points. The existing AI-driven mock rounds (`src/lib/interview/config.ts`, `InterviewSession.tsx`, `InterviewReport.tsx`) stay as they are for general practice; Phase 6 adds a **job-specific, deterministic, evidence-grounded** mode that reuses the round vocabulary (dimensions, coding/design briefs), the code editor (`AlgoEditor`), the Mermaid diagram editor, the interview CSS, the curriculum registry and quiz bank, the resume profile, the preparation blueprint and the roadmap plan engine.

- **Engine** (`src/lib/interview/jobInterview.ts`, pure): `buildInterviewContext` (job snapshot, resume projects/bullets, skill evidence from the resume analysis, compatibility summary, blueprint depths and items, curriculum progress, gaps) → `deriveInterviewConfig` (difficulty and depth from level; coding only when the blueprint's DSA depth is not `none`; system design only at the depth the level and listing justify) → `composeInterview` (sections intro → resume → fundamentals → technical → coding → design → behavioural → wrap-up, filled by focus weights inside the time budget). Question sources with provenance: curriculum quiz questions (key terms of the reference answer become expected concepts), job requirements, resume projects and bullets (only names and lines that exist in the stored profile), and generated role practice labelled "Recommended practice based on this role". Seeded rotation and `excludeKeys` avoid repeating questions across attempts when alternatives exist.
- **Adaptive follow-ups**: `analyzeAnswer` extracts evidence (concepts hit/missed, example, trade-off, STAR structure, complexity, edge cases, dry run, code/diagram shared, gave up) and `decideFollowUp` chooses clarify / simplify / example / probe a missed concept / trade-off / challenge within `maxFollowUps` per question (0 preview, 1 standard, 2 advanced). No AI call; no endless questioning.
- **Sessions** (`src/lib/server/interviews.ts`, table `job_interview_sessions`, migration `0010`): configuration, context snapshot, plan, every turn with its evidence, cursor state, entitlements at start, report, plan-added marker. `jobId` is `SET NULL` on job deletion and the job snapshot keeps history readable; rows cascade with the user. All reads and writes are scoped by `userId` (other learners get 404). Routes: `GET/POST /api/jobs/[id]/interviews` (history, derive, start with daily and monthly limits), `GET/POST /api/interviews/[id]` (session, turn, complete, abandon, plan_added), `GET /api/interviews`.
- **Report** (`buildReport`): strong areas and needs-improvement from per-area concept counts, missed concepts, communication, coding (approach, correctness reasoning from the dry run, complexity, edge cases), system design (requirements, architecture, trade-offs, scalability, reliability), behavioural (examples, completeness), question-level feedback (question → answer → evidence → strength → weakness → better approach → related curriculum), weaknesses merged by curriculum topic. No score, verdict or hiring probability. `compareAttempts` reports `demonstrated/total` per area between attempts; `interviewReadiness` feeds `computeReadiness` with factual state only.
- **Feedback loop**: weaknesses with a `TopicPointer` become a pseudo-blueprint for `buildPreparationPlan` (the existing roadmap engine), so "Add weaknesses to learning plan" previews first, never duplicates scheduled or completed steps, and tags tasks with `prepJobId`. Re-attempts: full, weak areas (focus on the parent report's areas and topics), one section, or missed concepts (one drill per concept).
- **Entitlements** (centralised, admin-editable per plan): `interview.jobPreview` (free: three questions, no follow-ups, summary-only report), `interview.jobFull`, `interview.adaptive`, `interview.coding`, `interview.systemDesign`, `interview.feedbackDetailed`, `interview.curriculumMapping`, `interview.reattempt`, `interview.history`; limits `interviewsPerDay`, `interviewsPerMonth`, `interviewMaxMinutes`. No plan-name checks in components.
- **UI**: job workspace tab "Mock interview" (`InterviewTab`: derived configuration, device check and voice settings, the interview room, history with factual comparison; `InterviewSessionView`: the live room; `InterviewReportView`: debrief with replay). The general Mock Interview workspace lists job-specific attempts and links to the job.

### 7c.1 Voice-first interview room (Phase 10)

The same deterministic engine now talks like a human interviewer and is voice-first; nothing about state, timing, entitlements, provenance or persistence moved to AI.

- **Conversational layer** (`src/lib/interview/conversation.ts`, pure): `buildOpening` (greeting by first name when it looks like one, round description and length from the real configuration, invitation to ask for clarification, then the intro question; never claims to represent the company), neutral acknowledgements and section transitions that rotate and never praise or teach (`acknowledge`, `transition`, `isNeutral` guard), `classifyCandidateMessage` (repeat / clarify / assumption / thinking versus a real answer) with `clarificationReply` (design requirements revealed progressively, coding constraints, behavioural and resume clarifications; bounded to three per question), session memory (`extractFacts` from what the learner actually said, `relevantFact` + `personalize`: "Earlier you mentioned…", each fact used once), `manageTime` (drops later optional questions to fit the budget, keeps one question per section and the wrap-up, tolerates a modest overrun before cutting a section, never cuts an answer; at a minute left it heads to the wrap-up and asks no more follow-ups), `answerCandidateQuestion` (general interview-process answers only, never company facts; declines to assess mid-interview), `FAREWELL`, `buildTimeline` (replay = transcript + timing from stored turn timestamps; no audio is stored).
- **Session service** (`src/lib/server/interviews.ts`): the opening is stored as the first interviewer turn; every interviewer line is a turn (`opening`, `question` as voiced, `follow_up` with a neutral `lead`, `transition`, `clarification`, `nudge`, `closing_answer`, `farewell`) and every learner turn too (`answer`, `follow_up_answer`, `skip`, `clarification_request`, `candidate_question`, with `input: voice | text` and client-measured `latency`). `SessionState` gained `phase` (interview → closing → ended), `memory`, `usedFacts`, `dropped`, clarification / nudge counters and `voice`. `SessionDto.say` is everything said since the learner's last turn (what to speak and caption; also what a refresh replays), `phase`, `interviewer.title`, `dropped`. New actions: `turn` kinds `clarify` and `nudge`, `wrap_up` (learner ends or the clock runs out while idle → wrap-up question, then farewell), and `complete` appends a farewell if one is missing so the report is only ever built after the closing. The report gained `clarificationsAsked`, `voiceUsed`, `timeline`, per-question `evaluating` (expected concepts) and `clarifications`; asked-but-unanswered questions are excluded. The AI gateway still only rephrases follow-ups (`interview.followup`, sensitive, one call per turn, failure keeps the deterministic wording).
- **Voice** (`src/lib/server/tts.ts`, `GET/POST /api/interviews/voice`): a TTS abstraction with adapters for OpenAI speech, Google Cloud TTS (Indian-English neural voices), ElevenLabs and a development-only silent-WAV fixture (`TTS_FIXTURE=1`, never in production); admin voice policy in `platform_settings.voice` (provider order, voice per provider, rate, locale, silence and end-of-speech thresholds, timeout, enabled) edited on `/admin/ai` (`VoiceConfigForm`, `voice` and `voice_probe` actions of `/api/admin/ai`). `GET` reports the device / connection check (voice entitlements, `tts.mode` **premium** only when a provider is configured *and* the learner has `interview.premiumVoice`, otherwise **browser** with `premiumConfigured` stating why; STT provider; AI availability; dev diagnostics flag). `POST` streams audio (`X-Voice-Provider`), or `204` + `X-Voice-Fallback: browser` (entitlement / not configured), or `503` + the same header on provider failure so the client falls back instead of losing the turn. Keys never leave the server.
- **Browser** (`src/lib/interview/voice.ts`, `speech.ts`, `useInterviewVoice.ts`): `createSpeaker` prefers the server voice (Audio element) and falls back to `speechSynthesis`, reporting the engine honestly (`premium` / `browser` / `off`) and never blocking a turn (start watchdog for silent engines); `listen` wraps Web Speech recognition with pause tolerance (restarts when the browser stops early, `no-speech` is not an error), silence callbacks, end-of-answer detection (`answerLooksFinished`) and a microphone probe; the hook orchestrates speaking → listening → processing states, silence nudges (`silenceNudgeLevel`: "Take your time." then an offer to repeat, both thresholds configurable and 0 disables them), automatic send after the end-of-speech pause with a visible 3-second cancel window (typing cancels), and latency measurement (STT finalisation, TTS start, full turn).
- **Room UI** (`src/components/interview/`): `InterviewRoom` (interviewer presence with speaking / listening / thinking states, realistic role identity "Technical Interviewer" / "Engineering Interviewer" / "Hiring Manager", stage indicator, clock, mute / captions / focus / leave / end, captioned utterance, transcript, status line with engine label, repeat and clarification actions, composer slot and coding / whiteboard workspace slot; `useFocusMode` hides the app chrome and warns before navigation; `useFullscreen`), `DeviceCheck` (microphone with level meter, "Test interviewer voice" with the test line, speech support, service, AI provider, each Ready / Fallback available / Unavailable; voice settings incl. accessibility thresholds; text-only always available), `InterviewTimeline` (replay). Job sessions: `InterviewSessionView`; general rounds: `InterviewSession.tsx` uses the same room and hook with the AI interviewer (prompt rewritten for neutral, time-aware, clarification-friendly behaviour and a role identity instead of a named persona), restores after a refresh from `sessionStorage` + the local transcript store.
- **Entitlements**: `interview.voice` (free and pro), `interview.premiumVoice`, `interview.replay` (pro); `interviewMaxMinutes` still bounds long interviews. No plan names in components.

## 7d. AI provider gateway (Phase 6.5) and company source catalog

**AI gateway** (`src/lib/ai/`, server binding `src/lib/server/ai.ts`): every AI call goes JobAppy → gateway → feature policy (`platform_settings.ai`, edited in `/admin/ai`) → provider/model (Gemini, Groq, Mistral, OpenRouter, OpenAI adapters; a deterministic fixture outside production) → timeout → retry with backoff or retry-after → fallback to the next provider → structured-output validation → usage accounting (`ai_usage_log`, metadata only) → error id. Keys stay in the environment or the learner's encrypted key. Features flagged sensitive (interview follow-up/feedback, resume insights, strategy narrative, draft refinement) are sent to exactly one provider and never fall back across providers; they carry structured facts, never the resume text. Every integration keeps its deterministic engine as the result of record and stores AI output as a labelled, validated addition (`aiRefined`/`deterministicText` on follow-ups, `aiSummary` on interview reports, `aiInsights` on resume analyses, `narrative` on the strategy response, `refined` on drafts).

**Company source catalog** (`src/data/companyCatalog.ts`, `src/lib/server/catalog.ts`, `/admin/catalog`): 60 curated companies relevant to Indian software, data, AI and cloud careers with canonical identity, official careers URL, India relevance, supported role families and provenance. A source is configured only where a public, documented job-board API (Greenhouse, Lever, Ashby) answered a read-only identity probe (19 companies on 2026-09-25); the other 41 are stored as `Not configured` / Unsupported with the careers link and are never ingested. Seeding is idempotent and keeps admin decisions; verification is read-only; scheduled ingestion is an explicit admin opt-in per source (`Schedule all verified`); ingestion goes through the existing engine, so only listings that normalise to a supported role family are stored (HR, sales, finance and operations postings are dropped as irrelevant). Statuses: Configured, Healthy, Degraded, Unsupported, Not configured.

## 7e. Onboarding and Career Command Center (Phase 8)

- **Onboarding** (`src/components/onboarding/OnboardingFlow.tsx`): twelve short steps (welcome → career target → experience → skills → resume → location → India/international → remote preference → learning availability → curriculum recommendation → job preferences → dashboard); optional steps skip. Every answer lands in an existing feature: the career target maps to a career path whose tracks become a real `Goal` with a roadmap from `generateRoadmap`, availability sets `hoursPerDay` and rest days, the resume goes through the existing upload API, and the job preferences are saved with `PUT /api/jobs/preferences`. Progress is stored as `preferences.onboarding` in the synced Storage document, so it survives refresh, sign-out and a new device. New accounts see the flow once on the Command Center; "Skip setup for now" records the skip and the Command Center offers to finish later.
- **Career Command Center** (`src/CommandCenter.tsx`, view `home`): cards for career goal, curriculum progress, today's learning, revision due, recommended jobs, recently verified jobs, applications, interviews, follow-ups due, job preparation, weak areas, mock interview progress, networking, upcoming tasks and profile/plan. Learning and tracker cards summarise the synced state; server-held facts come from one request (`GET /api/dashboard` → `src/lib/server/dashboard.ts`: ranked jobs, recently verified, outreach follow-ups due, preparations, interview history, resume and preference presence). Every card links to the real feature; there are no estimates.
- **Navigation**: `home` is the first item under Career Plan and the mobile Home group; signed-in learners land there once per session, guests keep the Today view (the free plan is job discovery and tracker; the roadmap stays behind the paywall as before).

## 8. Curriculum integration

- `src/lib/jobs/taxonomy.ts` defines role categories (Software Engineer, Frontend, Backend, Full Stack, Java Backend, Node.js, React/Next.js, Mobile, DevOps/Cloud, Data Analyst, Data Scientist, Data Engineer, AI/ML, Cybersecurity) and maps each to `careerPaths` ids. Tracks come from those paths; admins can pin extra `trackIds` on a job.
- `src/lib/jobs/curriculumMap.ts` (client) resolves a job to tracks through the registry, matches skills to tracks by tag/title/language, and folds in learner progress: a track is "in your plan" if a goal includes it, "started"/"completed" from roadmap task statuses and knowledge workspace statuses. Phase 2 adds "Add gaps to learning plan" using the existing `scheduleTrackIntoRoadmap` / `fillRoadmap` (no duplicate tasks because those helpers only add unplanned topics).

## 9. Subscription and entitlement architecture

**Phase 5 (2026-09-25) replaced the tier map with admin-managed plans.**

- `billing_plans` (migration `0009`): id/slug, internal name, display name, description, monthly and annual price in minor units, currency, active, default, highlighted, display order, `features` (feature keys), `limits` (every `LIMIT_KEYS` entry), `trialDays`, `providerPlanIds` (Razorpay plan ids per interval). Seeded once with FREE and PRO development fixtures (`SEED_PLANS`, not final pricing); edited in `/admin/plans` (audited `plan.create` / `plan.update`); plans are deactivated, never deleted (`billing_subscriptions.planId` is `RESTRICT`).
- `billing_subscriptions`: provider-independent lifecycle `pending → trialing/active → past_due → cancel_at_period_end → cancelled/expired` with `grantsAccess(row, now)` as the single access rule (7-day grace for `past_due`). `billing_events` is the webhook ledger (unique provider + event id: duplicates are detected before anything is applied; failures keep the ledger row with the error). `notification_log` records every notification attempt (`sent`, `skipped` without a mailer, `failed`).
- Resolution: `resolvePlanForUser` → allowlist → verified subscription → legacy one-time pass (`subscriptions` table, mapped to `legacyPaidPlan`) → default plan. `platformConfigFor` and `resolveAccess` read only this, so no route compares plan names. The legacy `getEntitlement` (AI/code-runner gates) also honours subscriptions.
- Providers (`src/lib/billing/providers`): `BillingProvider { createCheckout, cancelAtPeriodEnd, parseWebhook }`. `razorpay` uses Razorpay Subscriptions (checkout.js `subscription_id`, HMAC-SHA256 checkout and webhook signatures, cancel at cycle end); `fixture` is a deterministic signed provider available outside production only. `activeProvider()` picks Razorpay when keys exist, else the fixture, else none. Activation happens only through a signature-verified webhook (or the signature-verified Razorpay checkout handler owned by the caller); the client never sets billing state.
- Surfaces: `/pricing` (public; monthly/annual toggle, plan cards, current plan, upgrade / cancel entry point), Settings → Billing (plan, cycle, status, renewal, usage meters from `/api/billing/usage`, cancel renewal, delete Career OS data), `/admin/plans`, `/admin/subscriptions` (read-only), `/admin/billing` (webhook health, failed events), `/admin/launch` (live readiness checks).

Earlier phases (kept for context):

Implemented in Phase 2: `src/lib/server/entitlements.ts` (`resolveAccess`, `requireFeature`, `consumeUsage`) is the only server gate; `platformConfigFor` also returns per-tier limits (`platform_settings.limits`) and disabled role families. Free accounts keep job discovery, basic filters, job details, the official apply link and the tracker (feed capped by `limits.free.jobFeed`, newest first); Pro adds the personalised feed with sections and reasons, level/type filters, compatibility analysis, gap analysis and adding gaps to the plan. The `/app` paywall no longer blocks free accounts from those views (`FREE_VIEWS` in `App.tsx`) and offers "Continue on the free plan"; locked capabilities render through `LockedFeature`.

## 10. Security and RBAC

- Admin surfaces are server-checked (layout + every route handler); the SPA never receives admin data. Non-admins receive 404 for pages and 403 for APIs.
- Role changes are audited and an admin cannot remove their own `admin` role (prevents lock-out).
- Admin input is validated in `src/lib/jobs/normalize.ts` (`parseJobInput`) and equivalent parsers for companies / sources; URLs must be http(s).
- Learner preference writes require a session; reads of published jobs are public (same as `/api/curriculum`).

## 11. Data provenance

Every job row keeps `sourceId`, `sourceUrl`, `applyUrl`, `externalId`, `postedAt`, `lastVerifiedAt`, `createdBy`. The learner UI always shows company, source name, original apply link, posted date and last verified date. AI-derived content (Phase 2+) is stored separately and rendered with an "AI suggestion" label.
